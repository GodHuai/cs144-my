# 完整 QUIC v1 行为要求

以 RFC 9000/9001/9002 原文为准。本文件是验收摘要；`coverage.md` 在实现时细化到每条规范性要求。

## R1：连接与安全

- 双端完成版本协商、Initial、Handshake、1-RTT、Retry、连接 ID、token、传输参数、地址验证与反放大；满足 Initial 数据报长度要求。
- TLS 1.3 消息经 CRYPTO 帧传输；验证证书、主机名、ALPN、加密级别和认证标签；验证失败不向应用交付数据。
- 支持 0-RTT 凭据、发送、接受/拒绝。服务端不得处理已拒绝的 0-RTT 包；客户端拒绝时重置所有流及其关联应用状态，通知应用。应用数据仅在应用协议定义了 0-RTT 使用规则且应用明确请求时发送；互通适配层只允许只读 GET，其他操作等到 1-RTT。只有应用按重放安全策略重新发起请求，才在 1-RTT 上重发。服务端校验恢复配置并执行重放防护；API 明示早期数据的重放风险。密钥按 RFC 派生、更新与丢弃；包号不复用。

## R2：包、帧和生命周期

- 支持 v1 长/短包头、截断包号恢复、合并包、变长整数、三类包号空间及 RFC 9000 全部基础帧的合法状态和错误处理。
- 完整解密、认证、处理后才确认包；非法 ACK、长度、保留位、帧、状态和额度得到协议规定的处置。
- 支持空闲超时、正常/错误关闭、draining 与 stateless reset；未知连接不影响其他连接。

## R3：流与流量控制

- 双向/单向流分别维护 offset、方向、收发状态、FIN/final size、RESET_STREAM 和 STOP_SENDING；重复数据不重复交付。
- 遵守并增长每流、连接及并发额度；按各流最高偏移和 final size 记账，不按重复帧长度记账；违规触发正确错误。
- 对每条流，公布的接收上限不得超过其 Reassembler 可无损保存的窗口右端；只有应用消费腾出容量后才增长上限。通过认证、处理并将数据列入 ACK 的包，其额度内 STREAM 数据必须已无损保存；不能依赖被 ACK 后再次重传。乱序数据靠近上限时验证此约束。
- 一条流缺字节时，其他流的连续字节仍能交付。

## R4：恢复与拥塞

- ACK/ACK_ECN 表达离散包号范围与延迟；分空间追踪发包和 ACK，共享 RTT/拥塞状态。
- 实现 RFC 9002 的丢包阈值、PTO、慢启动、拥塞避免、恢复期、持续拥塞、bytes-in-flight、ECN 验证与发送节奏。
- 丢失信息装入新包号；迟到/重复 ACK、密钥丢弃和跨空间场景不误释放数据。

## R5：路径与网络

- 支持 Retry、PATH_CHALLENGE/RESPONSE、主动迁移、NAT 重绑定、连接 ID 更新及新路径状态。
- 支持 PMTU 探测和黑洞恢复、ECN 有效性检查与回退、IPv4/IPv6。
- UDP/地址层能收发 IPv4/IPv6，并读取/设置每个数据报的 ECN 标记；不能仅靠当前 IPv4 的 `UDPSocket` 接口通过这些验收。

## R6：证据和讲解

- 本项目双端互通，并通过 QUIC Interop Runner 的 HTTP/0.9 测试适配层分别与至少一种独立 QUIC v1 实现以客户端/服务端角色互通；记录对端版本、ALPN、配置和日志。
- 新旧测试、故障注入、模糊测试通过；`coverage.md` 逐条给出源码与验证证据。
- 实现后 `implementation.md` 按 RFC 条款对照实际代码，详解关键状态机和数据路径。

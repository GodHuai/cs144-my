# QUIC v1 行为要求

本文件定义 Minnow QUIC v1 项目的可观察行为。规范依据为 [RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html)、[RFC 9001](https://www.rfc-editor.org/rfc/rfc9001.html) 和 [RFC 9002](https://www.rfc-editor.org/rfc/rfc9002.html)。每项实现应按 RFC 原文核对 MUST/SHOULD 约束；下列场景是最低验收集，而非 RFC 全文的替代品。

## R1：协议身份与安全连接

- 客户端和服务端使用 QUIC v1 的线格式和版本号建立连接，能处理 Initial、Handshake 和 1-RTT 包。
- TLS 1.3 消息在 CRYPTO 帧中传输；应用数据仅在合适的密钥与握手状态下发送和接收。证书验证失败、载荷认证失败或不合法加密级别必须阻止应用数据交付。
- 正确派生 Initial 密钥，完成包载荷加密与包头保护；每个包号空间内发送包号不可复用。
- 客户端 Initial UDP 数据报满足 RFC 9000 的 1200 字节最小要求；服务端遵守地址验证前的反放大限制。
- 首轮不启用 0-RTT；不能接受或产生未协商的早期应用数据。

## R2：包与帧

- 编解码支持 QUIC 变长整数、连接 ID、长/短包头、截断包号恢复、合并包及首轮所需的帧类型。
- 接收包在去除保护、验证并完成帧处理后才能进入 ACK 集合；畸形长度、非法状态、流量控制违规和不被允许的帧应按 RFC 9000 的错误规则处理。
- 未知帧、保留位、版本协商、Retry 等边界按 RFC 9000 实现明确处理；不能将无法解析的网络输入默默当成有效数据。

## R3：多流与流量控制

- 双向流以 Stream ID 标识；数据用每流 offset 排序。每条流可以独立乱序接收、去重、交付和结束。
- FIN 指定 final size；同一流的最终长度冲突、最终长度之后还有数据，以及超过已公布额度的数据必须触发相应协议错误。
- 发送端遵守每流和连接级流量控制及并发流上限；应用消费数据后接收端可增长额度并通知对端。
- 一个流的数据缺口不阻止另一条已有连续数据的流向应用交付。

## R4：确认、丢包与拥塞

- ACK 帧能表达非连续包号范围；发送端维护按包号空间区分的已发送包记录与 RTT 样本。
- 实现 RFC 9002 的包阈值/时间阈值丢包判定、PTO、bytes-in-flight 与初始拥塞控制。丢失的可重传信息可重新封装进新包，且新包使用新包号。
- ACK 丢失、包乱序、重复包及数据包丢失时，不重复交付应用字节，也不提前释放仍需恢复的数据。

## R5：生命周期与互通

- 双端可主动建立连接、正常关闭和因传输错误关闭；空闲超时与连接 ID 路由行为明确。
- 本项目的客户端与服务端先完成 loopback 互通；至少再与一种独立 QUIC v1 实现完成握手、双向流传输和关闭测试。
- 第一轮允许暂不实现 0-RTT、HTTP/3、QUIC v2 和主动连接迁移。未实现能力须被拒绝或通过传输参数限制，不能宣称这些能力已经通过验收。

## R6：可验证性与实现文档

- 单元测试覆盖编解码、包号恢复、流状态、最终长度、流量控制与恢复算法；集成测试可控地注入丢包、乱序、重复和延迟。
- 现有 Minnow TCP 实验测试保持通过。
- 实现完成后提交详细文档，逐项列出 RFC 条款、对应代码、状态转换、测试证据和未支持能力；包含从 UDP 数据报到应用流交付，以及从 ACK/PTO 到重新发包的完整示例。

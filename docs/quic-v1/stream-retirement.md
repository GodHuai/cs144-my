# 流终态回收与 MAX_STREAMS 补额

在可靠应用流基础上，`ApplicationStreams` 现在回收已完成的流状态，释放并发槽位，并通过可靠 MAX_STREAMS 更新让长连接继续创建新流。128 从累计生命周期限制改为每方向每发起方同时占用的资源上限；流 ID 仍单调递增，不回收编号。

## 什么时候可以回收

| 半部 | 终态条件 |
| --- | --- |
| 发送 FIN | FIN 已确认，且此前所有发送数据都已确认 |
| 发送 RESET | RESET 已确认；旧 STREAM 的逻辑重传任务随后取消 |
| 接收 FIN | 所有最终大小以内的字节已读取，应用已观察 EOF |
| 接收 RESET | 应用通过 read 观察了 reset_error |

单向流只检查其合法半部；双向流必须两半都满足条件。FIN 尾部先被 ACK 不代表缺失前缀已确认；尚未读取的接收数据和未观察的 reset_error 都不能静默回收。接收终止一旦被应用观察就保持这一事实：双向发送半部仍活动时，迟到 RESET 不会重新制造一次读取义务。

最终一次 `read_stream` 仍返回应有的字节、EOF 或 reset_error，再释放重状态。之后 `stream_ids()` 只枚举活动的实体化状态，读取旧 ID 返回空且非 EOF，写入/reset/stop 返回 false。应用若需要保留已结束流的结果，应自行保存，不应依赖连接无限保存终态对象。

## 并发与累计编号的区别

初始 `initial_max_streams_uni=1` 时，对端只能开第一条单向流。它完成并被本端应用观察后，本端把累计 MAX_STREAMS 更新为 2；对端才能开第二条。每次完成只增加一次，重复 FIN/RESET/ACK 不重复补额。更新是单调绝对值，未发送更新合并，已发送更新由已有丢包恢复可靠重传。

本端回收自己发起的流，只释放本地资源槽位；它不能替代对端的 MAX_STREAMS 授权。即使本端已有空槽，也不能越过对端许可。对端给出大于 128、最高 2^60 的合法初始额度仍被接受；本端同时活动的资源上限独立为 128。累计上限封顶 2^60，ID 计算之前先检查许可，避免溢出和编号复用。

隐式打开的低编号流也占额度：例如先收到同类 ordinal=2，ordinal=0/1 不能因为尚未分配对象就当成关闭。只有真正完成的流才补额。

## 如何记住关闭 ID

按 ID 最低两位区分四类流，分别保存关闭 ordinal 的合并闭区间。比如已关闭 0、2、3，但 1 仍活动，保存 `[0,0]` 和 `[2,3]`；1 完成后合并为 `[0,3]`。不会保留每一条已关闭流的完整缓冲或逐 ID tombstone；区间数量随仍未结束的缺口数增长，受并发资源界限约束，而非随历史流数增长。

迟到的合法流帧命中关闭区间后直接忽略，不重新建状态、不重新计入流控，也不重复补额。方向错误仍报 STREAM_STATE_ERROR；STREAM 偏移加长度的溢出检查位于关闭分支之前，不能被“忽略旧帧”绕过。关闭后可以丢弃逐流最终大小细节，因此本实现不再检查这些已遗忘最终大小的矛盾；活跃流仍严格检查。依据 [RFC 9000 §4.5](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.5) 和 [§4.6](https://www.rfc-editor.org/rfc/rfc9000.html#section-4.6)。

## RESET 的恢复清理

RESET 尚未交付时，已发送数据仍占发送缓冲额度，不能通过取消绕开 1 MiB 接纳上限。RESET 首次被 ACK 后，应用发送缓冲释放剩余数据；恢复层在 ACK 区间遍历之后取消该流的旧 STREAM 共享逻辑任务，避免回调内重入修改恢复容器，也避免继续排队过时副本。

这不等于旧物理包被确认：其 bytes-in-flight 仍等待实际 ACK、丢失或密钥/连接退役结算。取消旧 STREAM 不产生虚假的应用交付回调。恢复层仍保留有界近期历史，不能把“应用流状态已回收”理解成历史物理记录立即全部消失。

## 测试与边界

独立流测试在单额度下连续完成 300 条单向流；覆盖双向两半、未读结果、FIN 缺失前缀、隐式低编号缺口、区间合并、迟到帧、重复关闭、合法大初始额度及本地活动上限。恢复测试覆盖 RESET ACK 取消排队探测、迟到旧 ACK 不产生交付，以及独立物理在途。

受保护连接 `quic_stream_retirement` 连续运行 129 轮双向请求/应答与单向流，初始流额度均为 1，包含空 FIN、周期性字节数据及首次 MAX_STREAMS/ACK 丢失。原有 9 KB 数据传输、乱序重传和小字节窗口测试仍由 `quic_stream_connection` 覆盖。两者是同一测试程序的两个 CTest 入口，分别运行；避免把独立场景的总运行时间挤进单个 30 秒上限。

仍缺连接监听/多路分发、主动关闭及 idle/closing/draining 计时、持续拥塞/ECN、会话恢复/0-RTT、迁移、密钥更新、PMTU 和外部互通。这轮不改变这些范围。

最终全量 CTest：**57/64 通过**（165.45 秒），其中 QUIC **26/26**（包含公共编译夹具，24 个 QUIC 测试程序；应用流连接程序注册两个入口）。新增连续建流场景耗时 25.66 秒。五项既有超时为 `wrapping_integers_roundtrip`、`wrapping_integers_extra`、`recv_transmit`、`recv_reorder_more`、`send_transmit`；`net_interface`、`router` 缺少可执行文件，无新增失败。

新入口显式设置 CTest `TIMEOUT 30`，覆盖普通测试目标的全局 12 秒默认值；另以 `--timeout 12` 单独验证该属性生效。全量测试命令：`ctest --test-dir build --output-on-failure --timeout 30 -j2`。
